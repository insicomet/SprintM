## Вертикальные связи: подтверждённое расхождение формулы

Excel использует:

```text
C96=(4*(C10+0,5)*J87
    +L85*K95*C9
    +(4*2)*L92*L85*1,1
    +(2*2)*L93*L83*1,1)
    +0,436+J85*L156
```

Входы книги:

```text
J87=0,0194       масса стойки/уголка 160×4, т/м
L85=0,0072       горизонтальная связь, т/м
L83=0,011        вертикальная связь, т/м
K95=3            число распорок
L92=L93=√(6²+5²)=7,810249676 м
J85=0,0096       уголок 80×4, т/м
L156=64          периметр двух окон после округления ширины к шагу 5 м
```

SprintM: `src/calc/frame/bracing.ts:190-207`, функция `computeBracing`.
В ней горизонтальная и вертикальная составляющие используют одну и ту же
`braceTube_t_per_m = TUBE_MASS_t_per_m[BRACE_TUBE]`, где `BRACE_TUBE = "80х3"`
и масса `0,0072 т/м`. Это соответствует Excel для горизонтальной части, но
не соответствует `L83=0,011` для вертикальной.

Ручная разница только от этого места:

```text
4 × 7,810249676 × 1,1 × (0,011 − 0,0072)
= 0,13073019 т
```

Наблюдаемая разница между Excel и SprintM по строке «Конструкции из труб»:

```text
Excel C96 = 2,85967350 т
SprintM    = 2,72862613 т
Δ          = 0,13104737 т
```

Расхождение совпадает с ручной оценкой с учётом округлений и является
кандидатом на ошибку формулы SprintM с высокой уверенностью. Формулу пока не
меняю: нужно подтвердить профиль вертикальных связей ещё минимум на двух
независимых книгах.

## М16: конфликт ручной строки Excel и банка SprintM

Excel:

```text
O88 = 300 + 30*(K90−2)/K90 + 12*4/K90 + 12*2/K90
C93 = O88*K90 = 332,4×5 = 1662 шт.
```

`K90=I17=5`. Число `300` в `O88` — константа, не ссылка на строку банка.
SprintM передаёт в `computeFrameFasteners` значение `selection.bolts.totalInFrame`
из выбранной строки банка; для текущего подбора это даёт 1382 шт.

Категория: **разные источники входа / ручная вставка Excel**, а не доказанная
ошибка формулы SprintM. Для исправления нужны исходная строка банка 22069 или
подтверждение расчётчика, что ручное `300` действительно должно заменить
банковое значение.
